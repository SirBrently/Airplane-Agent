The council

Five lenses on the direction

Each perspective was asked the same thing: is this the most efficient way forward, and where does it break?

Pragmatic Engineer
The Node server already does the hard part. The real risk now is duplicating logic across Make and code — anything we push into Make.com is invisible to git, untestable, and fails silently. Keep Make as thin glue, not a second brain.
Cost / Efficiency Hawk
Nobody counted the Google bill. Each lead fires ~20 Places calls. At medium volume that's real money, and the endpoint-side cache is the single biggest lever — it cuts cost and latency at once. The cache isn't "later," it's the efficiency play.
Product / Sales
The human call steps are the whole point. Staff need a visible, editable list of leads and status — that's why Airtable earns its place over a pure-code database. Automate the reminders, not the relationship. And "potential fit" in every template, never "interested."
Reliability / Ops
Six services sit in the critical path, synchronously. If Places is slow, the Jotform-facing call hangs. The 5–10 minute SLA is generous, so eventually make the report async — ack instantly, search in the background. One retry path, not six.
Data Architect
Place ID as the dedupe key is right. But decide now whether Airtable is the system of record or just a view — two writers to one table means drift. Let Make link operators by Place-ID upsert; don't hand-roll the join.
Converged

What all five agreed on

  • 1The Node server is the brain; Make.com is thin glue. Search, ranking, and report generation stay in code. Make only triggers, moves data, and sends mail.
  • 2Airtable stays — as the single system of record. Its staff-visibility is a feature for the human call steps, and one writer (Make) keeps it clean.
  • 3Follow-ups are one scheduled scan over Next Action Date ≤ today — not a web of per-lead timers.
  • 4The credibility rule lives in the templates. Every message says "potential fit"; demand is never implied as confirmed.

Efficiency

Google Places cost model

Sized for the decided volume of 100–800 leads/mo. Each lead currently costs roughly $0.30–0.50 in Places calls (≈7 text searches + up to 14 detail lookups + geocode). The endpoint cache reuses operators across nearby leads, avoiding an estimated 40–60% of calls at steady state.

List-price estimates before any Google free-tier credit; actual SKUs and rates vary. Cache figures assume ~50% call reuse.

The takeaway that set the roadmap: at 400/mo the cache roughly halves the bill and cuts latency — enough to build it soon, not enough to block launch on it.

Roadmap

  • Match operator demand to specific aircraft types
  • Revisit system-of-record if volume passes ~800/mo
